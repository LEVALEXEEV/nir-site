# Развёртывание на Helios

Сайт публикуется на две площадки одним workflow (`.github/workflows/site.yml`):

| | GitHub Pages | Helios ИТМО |
|---|---|---|
| Адрес | [levalexeev.github.io/nir-site](https://levalexeev.github.io/nir-site/) | [se.ifmo.ru/~s505996/nir](https://se.ifmo.ru/~s505996/nir/) |
| Какие ветки | только `main` | `main` — в корень, остальные — в `preview/<ветка>/` |
| Способ | `actions/upload-pages-artifact` + `actions/deploy-pages` | `rsync` по SSH с отдельным deploy-ключом |
| Откат | повторный запуск старого workflow / revert | `helios-ops` → rollback, ≈ 0,5 с |

## Схема выкладки

```text
GitHub Actions                              helios.cs.ifmo.ru (FreeBSD, nginx → Apache)
──────────────                              ────────────────────────────────────────────
build: make content → mkdocs build --strict
       check_site.py (ссылки, внешние ресурсы)
helios:
  1. prepare  ───── ssh ─────────────────▶  удалить .incoming-* (обрывки прошлых деплоев)
                                            вернуть id текущего релиза
  2. rsync ─────────────────────────────▶   releases/main/.incoming-<id>/
     --link-dest=../<текущий>                (неизменённые файлы — жёсткие ссылки)
  3. activate ──── ssh ─────────────────▶   .incoming-<id> → <id>
                                            live/main → releases/main/<id>   (rename, атомарно)
                                            журнал history.log, чистка: хранить 5 релизов
  4. healthcheck ─ HTTPS ───────────────▶   https://se.ifmo.ru/~s505996/nir/
  5. при провале: rollback ── ssh ──────▶   live/main → предыдущий релиз
```

`~/public_html/nir` — симлинк на `~/nir-deploy/live/main`. Каждый релиз `main`
содержит ссылку `preview → ~/nir-deploy/live/preview`, где лежат ссылки на
текущие релизы веток. Так превью доступно по `…/nir/preview/<ветка>/`, но
хранится отдельно и не пропадает при выкладке `main`.

Логика на стороне сервера (`scripts/helios/remote.sh`) ничего не требует от
Helios, кроме `sh` и `rsync`: скрипт передаётся по `ssh … sh -s` при каждом
вызове и версионируется вместе с сайтом.

## Deploy-ключ

* Отдельная пара ed25519 только для CI; приватная часть — секрет
  `HELIOS_SSH_KEY`, публичная — в `~/.ssh/authorized_keys` на Helios.
  Пароль учётной записи в CI не используется и нигде не хранится.
* Ключ хоста закреплён в `scripts/helios/known_hosts` (отпечатки сверены с
  уже доверенным `known_hosts`); ssh запускается с `StrictHostKeyChecking=yes`,
  поэтому подменённый сервер ключ не получит. `ssh-keyscan` в CI не
  используется — он доверял бы любому ответившему.
* Ключ существует на runner только во время job (`$RUNNER_TEMP`, права 600) и
  удаляется в шаге `always()`.

## Healthcheck

`scripts/healthcheck.sh <url> <sha>` запрашивает опубликованный сайт снаружи,
до 6 попыток с паузой 10 с (кэш CDN GitHub Pages), и падает, если хоть что-то
не так:

| Проверка | Что ловит |
|---|---|
| главная: 200 и `<meta name="nir-build" content="<sha>">` | отдаётся не эта сборка (кэш, недоехавший деплой, откат) |
| страницы рисунков, таблиц, методики: 200 и контрольная строка | сломанные относительные пути в подкаталоге |
| `search/search_index.json`: 200 и «three.js» | поиск без индекса |
| `assets/katex/katex.min.js` и шрифт `.woff2`: 200 | формулы зависят от CDN / не доехали шрифты |
| `results/provenance.json` | нет метаданных происхождения |
| несуществующий путь → 404 со страницей сайта | ErrorDocument не настроен |

На этапе сборки `scripts/check_site.py` дополнительно запрещает ссылки от корня
домена (`href="/…"`) и внешние скрипты/стили/шрифты — формулы и поиск
работают без интернета.

## Откат

Релиз — полная копия сайта; публикация — замена симлинка. Поэтому откат — это
тоже замена симлинка, без повторной сборки и загрузки:

```bash
# локально (нужен deploy-ключ)
HELIOS_KEY=~/.ssh/helios_deploy HELIOS_KNOWN_HOSTS=scripts/helios/known_hosts \
  scripts/helios/deploy.sh rollback main            # на релиз перед текущим
scripts/helios/deploy.sh rollback main 20260922T120824Z-6e6a477   # на конкретный
scripts/helios/deploy.sh list main                  # релизы и журнал
```

или в GitHub: **Actions → helios-ops → Run workflow** (`rollback`, ветка,
id релиза), после отката workflow сам проверяет сайт healthcheck'ом с меткой
возвращённого релиза. Автоматический откат выполняется, если healthcheck
после выкладки не прошёл.

## Обрыв развёртывания на середине

Файлы загружаются в `.incoming-<id>`, который не опубликован. Пока симлинк
`live/main` не переключён, посетители получают прежний релиз целиком. Возможные
точки обрыва:

| Где оборвалось | Что видит посетитель | Что происходит дальше |
|---|---|---|
| во время `rsync` | старую версию целиком | следующий деплой удаляет `.incoming-*` и загружает заново |
| между `mv` и переключением | старую версию | новый релиз лежит, но не опубликован; следующий деплой продолжит штатно |
| во время переключения | старую или новую — `rename(2)` атомарен | — |
| после переключения, до healthcheck | новую версию без проверки | job упал → при следующем запуске healthcheck; откат вручную `helios-ops` |

Проверено на сервере: деплой, ограниченный 5 КБ/с, прерван через 8 с —
загружено 88 файлов из 120, healthcheck старой версии проходит, следующий
запуск сообщил «удаляю недокачанный релиз» и опубликовал новую версию.

Для сравнения, наивный `rsync --delete` прямо в `public_html/nir` при обрыве
оставил бы смесь версий: новые HTML со ссылками на ещё не загруженные ресурсы
и удалённые старые файлы. `concurrency` в workflow с `cancel-in-progress: false`
не даёт новому пушу оборвать идущую выкладку.
