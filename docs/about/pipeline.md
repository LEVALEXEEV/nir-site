# Конвейер «эксперимент → артефакт → страница»

Как результаты вычислений попадают на страницы сайта, где проходит граница
между «считаем в CI» и «считаем отдельно», и как сохранить связь
опубликованного результата с версией кода и данных. Лимиты CI приведены по
документации GitHub на сентябрь 2026 г.

## 1. Способы доставки результата на страницу

### 1.1. Статические изображения, сохранённые вручную (базовый вариант)

Автор запускает анализ у себя, копирует `figure.png` в `docs/` и коммитит.

* **Плюсы:** проще некуда; сборка сайта мгновенная и ничего не знает об анализе.
* **Минусы:** связи «картинка ↔ код ↔ данные» нет. Нельзя сказать, из какой
  версии данных построен рисунок, и нельзя проверить, что он вообще
  воспроизводится. Таблицы в Markdown переписываются руками и расходятся с
  CSV. Бинарные файлы раздувают историю git.
* **Когда годится:** одиночные иллюстрации, схемы, скриншоты — то, что не
  является результатом вычисления.

### 1.2. Исполнение ноутбуков на этапе сборки: nbconvert, MyST-NB, Quarto

Ноутбук — одновременно код анализа и текст отчёта. Генератор исполняет его и
встраивает выводы ячеек (графики, таблицы) в страницу.

| Инструмент | Как исполняет | Кэш / заморозка | Генератор сайта |
|---|---|---|---|
| **nbconvert** | `jupyter nbconvert --execute` или `ExecutePreprocessor` из Python | нет, надо делать самому | любой: вывод в Markdown/HTML |
| **MyST-NB** | при сборке Sphinx / Jupyter Book; `nb_execution_mode`: `off`, `force`, `auto`, `cache`, `inline` | `cache` — через jupyter-cache: ноутбук перезапускается, только если изменился его код | Sphinx, Jupyter Book |
| **Quarto** | `quarto render` исполняет `.qmd`/`.ipynb` через Jupyter (или knitr) | `execute: freeze: auto` — результаты в `_freeze/`, коммитятся; в CI перезапуска нет, пока не изменился исходник | собственный |
| mkdocs-jupyter | плагин MkDocs, `execute: true` | нет | MkDocs |

* **Плюсы:** текст и числа не расходятся — абзац стоит рядом с ячейкой,
  которая посчитала число; отчёт воспроизводится одной командой.
* **Минусы:** сборка сайта становится такой же тяжёлой, как анализ; в CI
  нужно полное окружение анализа (у нас это ~130 пакетов вместо ~20 для
  MkDocs); ошибка в ноутбуке валит публикацию. Кэш MyST-NB и `_freeze/`
  Quarto снимают стоимость, но кэш привязан к **коду ноутбука**, а не к
  **данным**: при новых данных с тем же кодом кэш «свежий», а результат —
  нет. Ключ кэша надо расширять хешем данных вручную.

### 1.3. papermill: параметризованные запуски

papermill исполняет ноутбук, подставляя значения в ячейку с тегом
`parameters` (добавляет после неё ячейку `injected-parameters`), и сохраняет
исполненную копию: `papermill analysis.ipynb out/s2.ipynb -p scenario s2 -p platform m4`.

* **Плюсы:** один шаблон — много отчётов (по сценарию, устройству, кампании);
  исполненный ноутбук с параметрами — сам по себе протокол запуска;
  естественно ложится на матрицу CI (`strategy.matrix`) или на батч-очередь.
* **Минусы:** papermill не публикует — нужен второй шаг (nbconvert / MyST-NB);
  параметры передаются как литералы, сложные конфигурации — через путь к файлу;
  отладка «почему этот запуск другой» требует сравнения ноутбуков.
* **Когда годится:** однотипные отчёты по многим срезам данных. В этом
  проекте — отчёт на каждое устройство × браузер пула (одна ячейка
  `parameters` с фильтром `PLATFORMS`).

### 1.4. Отдельный скрипт генерирует Markdown и CSV (Makefile / nox)

Скрипт читает данные, пишет `figures/*.svg`, `tables/*.csv` и готовые
`.md`-фрагменты; генератор сайта о вычислениях не знает. Порядок задаёт
Makefile (`site: content`) или nox-сессия (изолированное окружение на шаг).

* **Плюсы:** чёткий интерфейс между анализом и сайтом (файлы); можно
  кэшировать и переиспользовать шаг независимо; легко вставлять проверки
  (подпись есть у каждого рисунка, таблица совпала с эталоном); годится для
  любого генератора.
* **Минусы:** текст анализа отделён от кода — выводы в прозе могут устареть
  относительно чисел; нужен свой код генерации страниц.

### 1.5. Что выбрано здесь

Гибрид 1.2 и 1.4. `scripts/build_content.py` (вызывается `make content`):

1. исполняет ноутбук `benchmark/analysis/nir3_analysis.ipynb` через
   `ExecutePreprocessor` в копии каталога (рабочее дерево подмодуля не пачкается);
2. публикует ноутбук целиком без кода как [«Отчёт анализа»](../results/report.md)
   — текст и числа из одного запуска;
3. из `figures/` и `tables/` строит галереи с подписями из
   `content/captions.yml`; артефакт без подписи или подпись без артефакта —
   ошибка сборки;
4. сравнивает каждую пересчитанную таблицу с закоммиченной побайтно и пишет
   [метаданные происхождения](../results/provenance.md).

Для детерминизма SVG задаются `SOURCE_DATE_EPOCH` (время коммита benchmark)
и `svg.hashsalt`: без них каждый рисунок отличался бы датой и случайными id
путей, и хеш артефакта был бы бесполезен.

## 2. Ограничения CI для тяжёлых вычислений (GitHub Actions)

| Ограничение | Значение | Что это значит для вычислений |
|---|---|---|
| Время job на GitHub-hosted runner | 6 ч | длинное обучение/симуляцию надо резать на части с промежуточными артефактами |
| Время всего workflow | 35 дней | не ограничивает на практике |
| Минуты | публичный репозиторий — бесплатно; приватный на Free — 2000 мин/мес (Linux ×1; macOS ≈ в 10 раз дороже) | часовой пересчёт на каждый push в приватном репо съест лимит за неделю |
| Ресурсы стандартного runner (Linux) | публичный: 4 CPU, 16 ГБ RAM, 14 ГБ SSD; приватный: 2 CPU, 8 ГБ | датасет > ~10 ГБ не помещается на диск, модель > 16 ГБ — в память |
| GPU | нет на стандартных runner; GPU-runner — только «larger runners» на планах Team / Enterprise, платно | всё, что требует CUDA, в бесплатном CI не выполняется |
| Кэш (`actions/cache`) | 10 ГБ на репозиторий; неиспользуемый 7 дней — удаляется; при переполнении вытесняются самые старые; ветки видят кэш только своей и основной ветки | кэш — ускоритель, а не хранилище: результаты расчёта в нём могут исчезнуть в любой момент |
| Артефакты | хранилище 500 МБ на Free (для приватных); по умолчанию 90 дней | промежуточные данные между job ограничены по объёму и сроку |
| Параллельность | 20 одновременных job на Free, матрица ≤ 256 job | «распараллелить на 1000 узлов» нельзя |
| GitHub Pages | сайт ≤ 1 ГБ; деплой ≤ 10 мин; мягкий лимит трафика 100 ГБ/мес | тяжёлые исходные данные на сайт не выкладываются — только сводки |
| Среда | нет браузера с реальным GPU и дисплеем, чужое железо, шумные соседи | **измерения производительности в CI бессмысленны** — ровно наш случай |

## 3. Граница между стратегиями

**Стратегия A — вычисления в CI.** Сайт собирается из исходных данных,
анализ выполняется при каждой сборке.

**Стратегия B — вычисления отдельно.** Тяжёлое считается на своём железе /
кластере / GPU; в репозиторий (или хранилище данных) попадают готовые
артефакты; CI только собирает сайт.

Граница проходит не по «тяжести» вообще, а по четырём вопросам.
Вычисление остаётся в CI, только если на **все** ответ «да»:

1. **Детерминировано и воспроизводимо на чужом железе?** Статистика с
   фиксированным seed — да; замер FPS, обучение на GPU с недетерминированными
   ядрами — нет.
2. **Укладывается в ресурсы runner с запасом?** Ориентир: ≤ 10–15 минут и
   ≤ половины RAM/диска стандартного runner; иначе каждый push превращается в
   ожидание, а приватный репозиторий — в счёт.
3. **Входные данные доступны CI целиком и легально?** Сырые данные
   ≤ единиц ГБ, без персональных данных и лицензионных ограничений.
4. **Нужен ли пересчёт при каждом изменении сайта?** Если данные меняются
   раз в месяц, а текст — каждый день, пересчитывать нечего.

В этом проекте граница проходит **внутри** конвейера:

| Этап | Где | Почему |
|---|---|---|
| Замеры в браузерах (кампании r1, r2 …) | вне CI, на устройствах пула | нужен реальный GPU, дисплей, контроль питания и фона; часы на серию |
| Сырые результаты `results/**` (1591 файл, ~200 МБ) | коммитятся в benchmark | это и есть «готовый артефакт» стратегии B |
| Статистика, рисунки, таблицы | **в CI**, каждая сборка | ~30 с, детерминировано (seed, бутстрап), 14/14 таблиц совпадают побайтно |
| Сайт | в CI | — |

То есть для измерений применяется стратегия B, для анализа — A: CI
пересчитывает всё, что можно пересчитать, и тем самым проверяет, что
опубликованные числа следуют из закоммиченных данных.

## 4. Связь результата с версией кода и данных (стратегия B)

Если CI собирает сайт из готовых артефактов, каждый опубликованный артефакт
должен нести ответ на вопрос «откуда ты». Минимальный набор метаданных:

| Что | Как фиксируется здесь | Зачем |
|---|---|---|
| Версия кода, который произвёл данные | коммит benchmark = коммит подмодуля в репозитории сайта; в каждом `manifest.json` серии — свой коммит стенда и признак «дерево было чистым» | воспроизвести расчёт |
| Версия данных | хеш дерева `git rev-parse HEAD:results` — контентный адрес всего датасета; меняется при изменении любого файла | отличить «тот же код, новые данные» |
| Версия анализа | sha256 ноутбука + lock-файл пакетов (`requirements.txt`) | те же данные, другая статистика |
| Контрольные суммы артефактов | sha256 каждого SVG/CSV в `provenance.json` и на странице рисунков | проверить, что скачанный файл — опубликованный |
| Метаданные запуска | время сборки, ссылка на запуск CI, версия Python и пакетов, длительность; для замеров — устройство, браузер и его версия, условия (в manifest серии) | объяснить расхождения |
| Метка сборки на странице | `<meta name="nir-build" content="<sha сайта>">` | healthcheck убеждается, что отдаётся именно эта версия |

Если данные слишком велики для git, тот же принцип реализуется внешним
хранилищем с контентной адресацией: DVC (`.dvc`-файл с md5 в git, данные в
S3/SSH-хранилище), git-annex, или релизы с артефактами и sha256 в манифесте.
Важно одно: **в git лежит неизменяемый указатель на данные**, а не «последняя
версия» по изменяемому URL.
