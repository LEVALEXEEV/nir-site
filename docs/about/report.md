# Отчёт о работе

Статический сайт с результатами НИР на генераторе **MkDocs + Material**, с
автоматическим деплоем на **GitHub Pages** и **Helios ИТМО**. Данные
генерируются внутри пайплайна деплоя. Теоретическое задание —
[«Конвейер «эксперимент → артефакт → страница»»](pipeline.md), подробности
практического — [«Развёртывание на Helios»](deploy.md).

| GitHub Pages | [levalexeev.github.io/nir-site](https://levalexeev.github.io/nir-site/) |
| Helios | [se.ifmo.ru/~s505996/nir](https://se.ifmo.ru/~s505996/nir/) |

## 1. Ход работы

**1–3. Python, pip, virtualenv, окружение.** Python 3.13.7 (Homebrew),
pip 25.2. `python3 -m pip install virtualenv` отказал (PEP 668:
«externally-managed-environment», см. журнал), поэтому virtualenv 21.9 установлен
через `brew install virtualenv`. Окружение: `virtualenv -p python3.13 .venv`,
`source .venv/bin/activate`.

**4. Зависимости и .gitignore.** `requirements.in` — прямые зависимости
(mkdocs 1.6.1, mkdocs-material 9.7.7, pymdown-extensions, pyyaml и пакеты
анализа из `benchmark/analysis/requirements.txt`); `requirements.txt` — полный
lock из `pip freeze` (130 пакетов, точные версии). `.gitignore` исключает
`.venv/`, `site/`, `site-*/`, `_build/`, `_work/`, `docs/results/`, кэши.

**5. Каркас.** `mkdocs.yml` + тема Material (русский язык, светлая/тёмная
тема, `font: false` — без Google Fonts), `overrides/main.html` — метка сборки,
KaTeX 0.18.7 положен в `docs/assets/katex` скриптом `scripts/vendor_katex.sh`
с проверкой sha512 архива из npm.

**Генерация данных.** `make content` → `scripts/build_content.py`: исполняет
ноутбук анализа из подмодуля (≈ 15–20 с в CI), строит страницы
[«Отчёт анализа»](../results/report.md), [«Рисунки»](../results/figures.md)
(7 SVG + PNG), [«Таблицы»](../results/tables.md) (14 CSV → Markdown) и
[«Происхождение данных»](../results/provenance.md). Подписи — в
`content/captions.yml`; артефакт без подписи — ошибка сборки.

**6. Локальная сборка.** `make serve` — предпросмотр,
`make site` = `mkdocs build --strict` + `scripts/check_site.py`. Режим
`--strict` включён и в `mkdocs.yml`, так что его нельзя забыть в CI.

**7. Git и GitHub.** Репозиторий `nir-site`, `benchmark` — подмодуль на
фиксированном коммите (`710cbf7`). Репозиторий создан через `gh repo create`, код отправлен
`git push`.

**8. GitHub Actions и Pages.** Pages → Source = GitHub Actions
(`gh api -X POST repos/…/pages -f build_type=workflow`). Workflow
`.github/workflows/site.yml`: `build` → `pages` и `helios` параллельно.

**9. Helios.** Учётная запись `s505996`; отдельный deploy-ключ ed25519 добавлен
в `~/.ssh/authorized_keys` (пароль использован один раз и нигде не сохранён);
приватный ключ — секрет `HELIOS_SSH_KEY`. Сайт отдаётся из `~/public_html` по
адресу `https://se.ifmo.ru/~s505996/` (с `helios.cs.ifmo.ru/~s505996/` —
302-редирект туда). В `public_html` уже были другие работы, поэтому сайт
занимает подкаталог `nir/`, а деплой отказывается работать, если `nir` там —
не его симлинк.

**10. Workflow под площадку.** Job `helios`: rsync по SSH (порт 2222, ключ хоста
закреплён в `scripts/helios/known_hosts`), атомарное переключение релиза,
healthcheck, автооткат. Отдельно `helios-ops.yml`: ручной откат, список
релизов, удаление превью при удалении ветки.

**11. Базовый URL.** `site_url: !ENV [SITE_URL, …]` — задаётся при сборке:
`https://levalexeev.github.io/nir-site/` для Pages,
`https://se.ifmo.ru/~s505996/nir/` для Helios,
`…/nir/preview/<ветка>/` для превью. Поэтому в CI две сборки из одного
контента. `use_directory_urls: true` (`page/index.html`) одинаково работает в
Pages и Apache. Все внутренние ссылки относительные; `check_site.py` запрещает
ссылки от корня домена. От `site_url` зависят только canonical, sitemap и
`404.html` — у 404 пути абсолютные, поэтому 404 на Helios подключена через
`.htaccess` (`ErrorDocument 404 /~s505996/nir/404.html`) с путём своей цели.

**12. Проверка результата.** Не визуально, а автоматически (`scripts/healthcheck.sh`):
HTTP 200 и метка `<meta name="nir-build" content="<sha>">` на главной, контрольные
строки на страницах рисунков/таблиц/методики, индекс поиска, KaTeX и его шрифт
с самого сайта, `provenance.json`, 404 от сайта. Дополнительно проверено в
Chromium (Playwright) с **заблокированными запросами ко всем внешним хостам**:
на странице «Методика» отрисованы все 19 формул, ошибок KaTeX 0; поиск на
обеих площадках находит «задержка» (5), «бутстрап» (3), «ёмкость» (4) — работает
русский стеммер.

**13. Лицензии.** `LICENSE` — MIT на код; `LICENSE-CONTENT` — CC BY 4.0 на
тексты, рисунки, таблицы; KaTeX — MIT (`docs/assets/katex/LICENSE`).
Сводка — на странице [«Лицензии»](license.md).

## 2. Два способа публикации на GitHub Pages

| | push в `gh-pages` (`peaceiris/actions-gh-pages`) | `upload-pages-artifact` + `deploy-pages` (используется) |
|---|---|---|
| Что публикуется | коммит собранного сайта в отдельную ветку; Pages раздаёт ветку | tar-архив как артефакт запуска; Pages раздаёт конкретный деплой |
| Права workflow | `contents: write` — может писать в репозиторий | `pages: write` + `id-token: write` (OIDC), репозиторий только на чтение |
| Настройка Pages | Source = Deploy from a branch (`gh-pages`) | Source = GitHub Actions |
| История | вся история сайта в git: легко смотреть и откатывать `git revert`, но репозиторий пухнет бинарными файлами | в git ничего; история — в Environments → github-pages; артефакт живёт недолго (по умолчанию 1 день) |
| Защита | нет окружения и правил развёртывания | окружение `github-pages`: разрешены только выбранные ветки, можно добавить ревьюеров |
| Когда лучше | нужен просмотр/откат сайта как файлов, сторонний хостинг читает ту же ветку | рекомендуемый GitHub путь; нет лишних коммитов |

Выбран официальный вариант: у него минимальные права и нет коммитов со
сгенерированным HTML. Откат Pages — повторный запуск (`Re-run jobs`) старого
успешного workflow, пока жив его артефакт, иначе `git revert` и новая сборка.

## 3. Журнал отладки

| # | Симптом | Причина | Исправление |
|---|---|---|---|
| 1 | `pip install virtualenv` → `externally-managed-environment` | Python из Homebrew защищён PEP 668 | `brew install virtualenv`; всё остальное — внутри `.venv` |
| 2 | Сборка `--strict` прошла, но `check_site.py`: `<a href="/about/license/">` на всех 10 страницах | ссылка в `copyright` — сырой HTML, MkDocs её не проверяет и не переписывает; на Helios вела бы на `se.ifmo.ru/about/license/` — **та самая «типичная ошибка» подкаталога** | ссылка перенесена в шаблон: `{{ base_url }}/about/license/`; проверка ссылок от корня оставлена в CI |
| 3 | В «Отчёте анализа» нет ни одного рисунка | `MPLBACKEND=Agg` в окружении ядра отключает inline-бэкенд Jupyter: рисунки сохранялись в файлы, но не попадали в выводы ячеек | переменная убрана |
| 4 | Каждый SVG «меняется» при каждой сборке | matplotlib пишет дату и случайные id путей | `SOURCE_DATE_EPOCH` = время коммита benchmark, `svg.hashsalt` |
| 5 | После исполнения ноутбука подмодуль грязный (9 изменённых файлов) | ноутбук пишет `figures/`, `tables/`, `data/` рядом с собой | исполнение в копии `_work/analysis` со ссылкой на `results/` |
| 6 | в `pip freeze` на macOS попал `appnope` — зависимость ipykernel только для macOS; в CI (Linux) он лишний | lock снят на другой ОС, чем CI | маркер `; sys_platform == "darwin"` |
| 7 | `deploy.sh: link[@]: unbound variable` на первом деплое | bash 3.2 (macOS) при `set -u` считает пустой массив неопределённым | `${link[@]+"${link[@]}"}` |
| 8 | Деплой прошёл, а скрипт вернул 1 | последняя команда `[ -n "$GITHUB_OUTPUT" ] && …` при пустой переменной даёт статус 1 | `if … fi` |
| 9 | 404 на Helios — заглушка сервера, а не страница сайта | Apache не знает о `404.html` | `.htaccess` с `ErrorDocument` генерируется при деплое под путь цели |
| 10 | `deploy.sh list`: `sh: target: parameter not set` | во FreeBSD `sh` все подстановки в `target=$1 cur=$(f "$target")` выполняются до присваиваний | присваивания разнесены по строкам |
| 11 | `rollback`: «нет релиза для отката», хотя релизы есть | `log()` писал в журнал и имя цели, поля сдвинулись, awk искал действие не в той колонке | формат журнала исправлен, старые строки мигрированы |
| 12 | Healthcheck сломанного превью в CI висел, job снята по таймауту 10 мин, **автооткат не выполнился** | se.ifmo.ru после ~18 ответов 403 перестал отвечать IP runner'а → каждый запрос ждал таймаут 20 с (9 проверок × 6 попыток); отменённая job имеет статус `cancelled`, а откат стоял под `if: failure()` | healthcheck прерывает попытку при первой неудаче главной, `--connect-timeout 5 --max-time 10`, общий срок 150 с; у шага свой `timeout-minutes: 4` (шаг падает с `failure`, а не job отменяется); откат — `if: failure() \|\| cancelled()` |
| 13 | В логе `HTTP 000000` | `curl -w '%{http_code}'` сам печатает `000` при ошибке, `\|\| echo 000` дописывал второй | `\|\| true` |
| 14 | Русский поиск в автотесте давал 0 результатов | **ложная тревога**: Playwright вводит символы не из US-раскладки через `insertText` без `keyup`, а Material обновляет запрос по `keyup` | в тесте после ввода — нажатие `End`; поиск исправен. Реальное ограничение lunr: «емкость» не находит «ёмкость» (буква ё не нормализуется) |
| 15 | Material печатает баннер о несовместимости MkDocs 2.0 | MkDocs 2.0 ломает плагины и темы | версии `mkdocs==1.6.1`, `mkdocs-material==9.7.7` зафиксированы в lock |
| 16 | Ссылка `deploy.md#обрыв-развёртывания-на-середине` вела в начало страницы | стандартный slugify MkDocs выбрасывает кириллицу из якорей | `pymdownx.slugs.slugify`; `validation.anchors: warn` — при `--strict` битый якорь валит сборку |
| 17 | Доступ к GitHub API из автоматизации заблокирован | токен из связки ключей не должен извлекаться скриптами | авторизация `gh auth login` пользователем |

Ошибки 7, 8, 10–13 найдены только потому, что деплой, откат и обрыв
проверялись на настоящем сервере и в настоящем CI, а не «на глаз».

## 5. Сравнение GitHub Pages и Helios

Время — по двум запускам `main` в CI (push → опубликовано и проверено).

| Критерий | GitHub Pages | Helios |
|---|---|---|
| Общее время push → готово | 97 и 106 с | 122 и 114 с |
| Из них общая сборка (`build`) | 78–83 с (зависимости 39–43 с из кэша pip, ноутбук 16–20 с) | те же 78–83 с |
| Сама выкладка | `deploy-pages` 5–8 с | rsync + переключение 7–14 с из CI; **2–3 с** с машины в России |
| Healthcheck | 1 с | 9–13 с (≈ 1–1,4 с на запрос из дата-центра GitHub до ИТМО) |
| Превью веток | нет: у Pages один активный деплой на репозиторий | есть, `preview/<ветка>/` |
| Откат | повторный запуск старого workflow (пока жив артефакт) или revert + сборка: минуты | переключение симлинка: < 1 с, хранятся 5 релизов |
| Надёжность | CDN, высокая доступность, HTTPS из коробки; мягкие лимиты 1 ГБ / 100 ГБ трафика в месяц | один сервер за nginx; защита от частых запросов (из-за неё зависал healthcheck, п. 12); плановые работы вуза; зато доступен из российских сетей без CDN за рубежом |
| Удобство отладки | «чёрный ящик»: видны только статус деплоя и артефакт; нет логов сервера, нет доступа к файлам | ssh на сервер: файлы релизов, симлинки, журнал `history.log`, эксперименты с `.htaccess`; логов веб-сервера нет |
| Конфигурация сервера | нельзя (заголовки, редиректы, 404 — только `404.html`) | `.htaccess`: ErrorDocument, запреты, заголовки |
| Секреты | не нужны (OIDC-токен) | SSH-ключ в секретах + закреплённый ключ хоста |

**Обрыв развёртывания на середине.** *Pages:* артефакт сначала целиком
загружается, затем `deploy-pages` создаёт деплой, и GitHub переключает сайт
сам. Если отменить job, action отменяет незавершённый деплой, и остаётся
прежняя версия. Промежуточного состояния снаружи не видно, но и управлять им
нельзя. *Helios:* поведение задаёт наш скрипт. Загрузка идёт в неопубликованный
`.incoming-<id>`, публикация — атомарный `rename` симлинка, так что при обрыве
остаётся прежняя версия, а обрывок удаляется следующим деплоем
(подробнее — [таблица точек обрыва](deploy.md#обрыв-развёртывания-на-середине)).
Наивный `rsync --delete` прямо в `public_html` при обрыве оставил бы смесь
версий. Единственное окно, где посетитель может увидеть сломанную версию, —
между переключением и провалом healthcheck: в эксперименте п. 4 это ≈ 45 с
(5 попыток с паузой 10 с), потом срабатывает автооткат.

**Итог.** Pages проще и надёжнее как «просто хостинг». Helios требует больше
кода, но даёт то, чего у Pages нет: превью веток, мгновенный откат, полный
контроль и отладку на сервере. Выкладка на Helios с машины в России занимает
2–3 с; скорость загрузки страниц посетителями не измерялась.
